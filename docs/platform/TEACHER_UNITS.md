# Teacher Units (U1A Foundation, U1B Membership and Ordering)

**Status:** U1A implemented in the repository (Functions code, Firestore Rules, tests), including the Sol 6.1 certification remediation (transactional authorization snapshots, in-transaction school and district checks, create retry receipts, school-scoped listing). U1B (resource membership and unit ordering, section 9) implemented in the repository on top of U1A. **Not deployed.** No teacher UI calls these operations, so teacher units are not available to teachers. Nothing here is live until the Functions callables and the Firestore Rules blocks are deployed, and no product surface uses them until U2. Since A3-5 the Rules are callable-only: no client may read or write any Teacher Units document directly (section 7).

**Canonical for:** the `TeacherUnit` domain type, the `teacherUnits/{unitId}` and `teacherUnitCreateReceipts/{receiptId}` collections, the `teacherUnits*` callables, and their security, consistency, and concurrency contract.

---

## 1. TeacherUnit vs CurriculumUnit

| | `TeacherUnit` (this document) | `CurriculumUnit` |
| --- | --- | --- |
| Meaning | A teacher's own named instructional unit for one grade | One curriculum lesson card in the client manifest |
| Defined in | `platform/functions/src/shared/types/teacher-unit.ts` | `app/src/curriculum/curriculumManifest.ts` |
| Stored | Firestore `teacherUnits/{unitId}` | Bundled client data, never stored |
| Owner | One teacher, in one school | LyfeLabz curriculum |

The two types share no code and must not be merged or aliased.

## 2. Ownership

A unit is owned by exactly one teacher, in that teacher's school, for one grade (**teacher-grade ownership**). `teacherId` and `schoolId` come only from the caller's verified canonical identity (`requireDistrictContext`: the `users/{uid}` record wins over claims, and the school's `districtId` must match the signed claim). A request that names `teacherId`, `schoolId`, or any other server-owned field is rejected.

A unit stamped with a school that is no longer the teacher's current canonical school is not readable or mutable by that teacher (callables return `teacherUnits.notFound` or never read it; Rules deny). It is retained, not deleted or migrated. There is no recovery path in U1A (see section 11).

## 3. Storage

### `teacherUnits/{unitId}`

`unitId` is a server-generated Firestore auto-id (20 characters, `[A-Za-z0-9]`), globally unique and stable for the life of the unit. Callables reject any other id shape.

| Field | Type | Rule |
| --- | --- | --- |
| `teacherId` | string | Caller uid at creation. Immutable. |
| `schoolId` | string | Caller's canonical school at creation. Immutable. |
| `grade` | `"6"` \| `"7"` \| `"8"` | Same closed set as `classesActivate` and the teacher default-grade preference. Immutable. A Grade 8 unit is valid. Membership is not grade-restricted (section 9.1). |
| `title` | string | Trimmed, 1-120 code points, no control characters. |
| `description` | string | Trimmed, 0-1000 code points; line breaks and tabs allowed, other control characters rejected. Defaults to `""`. |
| `status` | `"active"` \| `"archived"` | |
| `archivedAt` | Timestamp \| null | `null` while active; server time of the archive transition while archived. |
| `createdAt` | Timestamp | Server timestamp. Immutable. |
| `updatedAt` | Timestamp | Server timestamp of the last accepted mutation. |
| `resourceIds` | string[] | Ordered canonical resource ids, each RA-1 `unitPlaceable`, no duplicates, at most 100. `[]` at creation. Written only by `teacherUnitsSetResources` (section 9.1). |
| `sortOrder` | number | `0` at creation. Written only by `teacherUnitsReorder`, which assigns positions `1..n` (section 9.2). |
| `revision` | integer | See section 6. |

No `districtId` is stored (the approved record does not include one); the district is resolved from the school on every call, and audit events carry it.

Reader order is `sortOrder` ascending, then `createdAt`, then `unitId`. Before any reorder this is creation order.

### `teacherUnitCreateReceipts/{receiptId}` (server-only)

One receipt per accepted create (section 5). Fields: `teacherId`, `schoolId`, `unitId`, `requestHash` (SHA-256 hex of the normalized grade, title, and description), `createdAt` (server timestamp), `expiresAt` (approximately seven days after creation, computed from the transaction attempt's clock, not the server commit timestamp that sets `createdAt`). `receiptId` is the SHA-256 hex of (operation, teacherId, schoolId, idempotencyKey). The raw key and the title and description text are not stored.

### Indexes

No composite index is required. The list callable and the reorder callable use two equality filters (`teacherId`, `schoolId`) with no ordering clause, which Firestore serves from the automatic single-field indexes. No TTL policy is configured (section 5.3).

## 4. Operations (Cloud Functions callables)

All require an authenticated, `active`, canonical `teacher` whose school resolves to the district on their signed claim (`role-forbidden`, `account-inactive`, `claim-*`, `school-district-mismatch`, `district-*` refusals otherwise). Every request uses a closed key allowlist (`teacherUnits.invalidRequest` names any extra field). Missing, another teacher's, and another school's units all return the same `teacherUnits.notFound`.

**A3-3 server contract (current server code; Teacher Units remains closed).** Every `teacherUnits*` callable first resolves the A3-2 runtime identity, then applies the authorization above, then enforces availability inside its transaction (section "U2.6 A3-3 transactional backend enforcement"). All six mutations additionally require the `compatibility` envelope, and create requires `expectedSchoolId`. With the production release-authority verifier (UNCONFIGURED), every list, get and mutation is refused. The request columns below include these A3-3 fields.

| Callable | Request | Effect |
| --- | --- | --- |
| `teacherUnitsCreate` | `grade`, `title`, `description?`, `idempotencyKey`, `expectedSchoolId` (required since A3-3, first attempts and replays; section 5.4), `compatibility` (A3-3) | Creates an active unit at revision 1, or replays the unit this key already created (section 5). Returns `{ unit, replayed }`. |
| `teacherUnitsList` | `includeArchived?` (default false), `grade?` (no `compatibility`; refused as `invalidRequest`) | Caller's own units in their current school, canonical order. Returns `{ units }`. Refuses (`teacherUnits.listLimitExceeded`) above 1000 records rather than truncating. |
| `teacherUnitsGet` | `unitId` (no `compatibility`; refused as `invalidRequest`) | One own unit, active or archived. Returns `{ unit }`. |
| `teacherUnitsUpdate` | `unitId`, `expectedRevision`, `title?`, `description?` (at least one), `compatibility` (A3-3) | Rename and/or edit description. Archived units are read-only (`teacherUnits.invalidStatus`). |
| `teacherUnitsArchive` | `unitId`, `expectedRevision`, `compatibility` (A3-3) | `active` -> `archived`, sets `archivedAt`. |
| `teacherUnitsRestore` | `unitId`, `expectedRevision`, `compatibility` (A3-3) | `archived` -> `active`, sets `archivedAt` to `null`. |
| `teacherUnitsSetResources` (U1B) | `unitId`, `expectedRevision`, `resourceIds`, `compatibility` (A3-3) | Replaces the unit's ordered resource list (add, remove, and reorder in one request). Archived units are read-only. Returns `{ unit, noop }`. Section 9.1. |
| `teacherUnitsReorder` (U1B) | `grade`, `units: [{ unitId, expectedRevision }]`, `compatibility` (A3-3) | Orders the caller's active units of one grade. Returns `{ units, noop }` (the grade's active units in canonical order). Section 9.2. |

Each unit is returned as `{ unitId, grade, title, description, status, archivedAtMillis, createdAtMillis, updatedAtMillis, resourceIds, sortOrder, revision }`. Single-unit mutations return `{ unit, noop }`.

There is no delete operation. U1A operations still reject `resourceIds` and `sortOrder` as request fields.

**Error mapping.** The canonical code is always in `HttpsError.details.code`. Coarse HTTPS codes: `teacherUnits.invalidRequest`, `.invalidIdempotencyKey`, `.invalidUnitId`, `.invalidExpectedRevision`, `.invalidGrade`, `.invalidTitle`, `.invalidDescription`, (U2.2) `.invalidExpectedSchoolId`, and (U1B) `.invalidResourceIds`, `.duplicateResource`, `.resourceNotPlaceable`, `.invalidUnitOrder` -> `invalid-argument`; `.notFound` -> `not-found`; `.writeConflict` -> `already-exists`; `.invalidStatus`, `.idempotencyKeyConflict`, `.listLimitExceeded`, (U2.2) `.schoolContextChanged` -> `failed-precondition`. The U1A and U1B validation codes are listed as exact codes in `shared/errors/https-callable.ts` (not suffixes), so `classes.invalidTitle`, `classes.invalidGrade`, and `accommodations.invalidExpectedRevision` keep their existing `failed-precondition` mapping. The twelve A3 codes (A3-3) are mapped exactly as `teacherUnits/a3-errors.ts` declares, before any suffix rule; see the A3-3 section for the table.

### 4.1 Authorization snapshot

`assertActiveTeacher` (`requireDistrictContext` plus the teacher role) runs first, outside any transaction, and fixes the actor (`uid`, `schoolId`, claim-verified `districtId`). Every operation then repeats the canonical checks **inside the Firestore transaction that reads or writes unit data**, against the same snapshot (`reassertTeacherContextInTransaction`):

- `users/{uid}` exists, `status == "active"`, `role == "teacher"`, and `schoolId` is still the actor's school (`account-inactive`, `role-forbidden`, `claim-state-mismatch`);
- `schools/{schoolId}` exists (`school-district-mismatch`), has a non-empty `districtId` (`district-unassigned`), equal to the actor's verified district (`district-mismatch`).

These are the same refusal codes `requireDistrictContext` uses for the same conditions. Schools have no status field, so existence plus district membership is the complete school authorization, as elsewhere in the platform. Ownership is then checked against the verified context, and writes and audit events use it.

- **Get** and every **post-mutation / post-create response** use `readOwnedTeacherUnit`: one read-only transaction that re-verifies authorization and reads the unit.
- **List** re-verifies authorization and runs its query in one transaction.
- **Mutations** re-verify authorization, read the unit, decide, and write in one transaction. A no-op response is built from that same snapshot.

**Consistency boundary.** Authorization and the data returned come from one transaction snapshot, and the user and school documents are in its read set. A suspension, role change, school transfer, school deletion, or district change committed **before** that snapshot is always honored. A change committed **after** the transaction completes cannot recall data already returned. After a committed write, the response is produced by a second authorized snapshot: if authorization or availability was revoked between the commit and that read, the write stands and the response is refused. Since A3-3, any failure after a confirmed commit is reported as `teacherUnits.responseUnavailable` with `outcome: "unconfirmed"`, never the underlying refusal code, and never the unit (historical: before A3-3 the caller saw the refusal code). For a create, retrying the same `idempotencyKey` once authorized again replays the unit.

## 5. Create retry contract

### 5.1 Behavior

`idempotencyKey` is required: a URL-safe token of 8-64 characters (`[A-Za-z0-9_-]`, the `labReportsSave.saveId` / RA-3A `operationId` grammar; a UUID fits). The client generates one key per intended unit and reuses it only to retry that same request.

In one transaction, after the authorization snapshot (section 4.1), the handler reads the receipt `teacherUnitCreateReceipts/{sha256(teacherId, schoolId, key)}`:

- **Absent:** create the unit (server auto-id), the receipt, and the `teacherUnits.created` audit event atomically. `replayed: false`.
- **Present, same normalized request:** a replay. The replaying attempt writes nothing and emits no audit event, so a confirmed replay never duplicates the unit, receipt or audit (attempt scope, section 6). The response is the original unit (same `unitId`) in its **current** state (it may have been renamed or archived since), with `replayed: true`.
- **Present, different normalized request:** `teacherUnits.idempotencyKeyConflict`; the refusing attempt writes nothing (attempt scope, section 6).

The request hash covers the normalized values (trimmed title and description, description defaulted to `""`), so `" Earth "` and `"Earth"` are the same request. Deduplication is by key only, never by title: two different keys with the same title create two units.

### 5.2 Concurrency and scope

Two simultaneous requests with the same scope and key map to the same receipt document. Exactly one transaction commits; the other is retried by Firestore (or loses the `create()` precondition and is re-run once), observes the receipt, and replays. If contention exhausts the retries, the request fails with `teacherUnits.writeConflict` and is safe to retry with the same key.

The receipt is scoped to the authoritative teacher **and** school. Another teacher using the same key, or the same teacher after a school transfer, gets a different receipt and a new unit; neither can reach the original unit through the key. A replay is authorized exactly like a first request (the authorization snapshot precedes the receipt read), so a suspended or transferred teacher cannot replay. Historical (before A3-3): without `expectedSchoolId`, a transferred teacher's same-key request was authorized in the new school and created a new unit there. Since A3-3 the field is required, so such a request is refused (`teacherUnits.schoolContextChanged`, section 5.4).

### 5.3 Receipt lifecycle and retention

- Exactly one receipt per created unit. A refusing or replaying transaction attempt writes no receipt and no audit event of its own; a receipt exists only because some attempt committed a unit with it. An earlier SDK attempt of the same request may have committed a unit, receipt and audit before a later attempt replays or refuses; that commit stands and is not duplicated (attempt scope, section 6). Receipts are therefore bounded by the number of units created.
- Receipts are never updated or deleted by any callable. Rules deny all client access.
- Each receipt carries `expiresAt`, calculated approximately seven days after creation (`TEACHER_UNIT_CREATE_RECEIPT_RETENTION_MS`) using the transaction attempt's clock rather than the server commit timestamp, so a Firestore TTL policy can remove it without a data migration.
- **No TTL policy is configured in U1A.** Adding one is a `firestore.indexes.json` field-override change (the index deploy surface, guarded by `platform/firebase/tests/firestore-indexes.rules.test.ts`) and needs separate authorization. Until then receipts persist, one per unit.
- A receipt is honored for as long as it exists, regardless of `expiresAt`. Once a TTL policy deletes it, the same key would create a new unit. The retry window that matters (a lost response, a reload) is seconds to minutes, far inside 7 days.

### 5.4 School binding: `expectedSchoolId` (U2.2; required since A3-3)

Receipts are scoped to the verified school (section 5.2). So if a create commits in school A, its response is lost, and the teacher's canonical membership and claims then move to school B, a same-key retry is authorized in B, finds no receipt there, and creates a second unit in B. That is an authorized cross-school duplicate, not an authorization bypass. `expectedSchoolId` closes it. U2.2 introduced the field as optional; A3-3 makes it mandatory for every v2 create, first attempt and replay.

- **Field.** Required (A3-3). A missing value, like a malformed one, is refused with `teacherUnits.invalidExpectedSchoolId` during validation, before any transaction (no write). Historical: under U2.2 the field was optional and its absence meant the U1A / U2.1 request; that request is no longer accepted. The value must be a canonical school id (`SCHOOL_ID_PATTERN` in `platform/functions/src/shared/types/school.ts`, the grammar `schoolsCreate` enforces), or the request is refused with `teacherUnits.invalidExpectedSchoolId` during validation, before any transaction (no write).
- **Comparison.** Inside the create transaction, immediately after the authorization snapshot (section 4.1) and **before the receipt is read or any write is staged**, `expectedSchoolId` must equal the verified school. Otherwise the attempt is refused with `teacherUnits.schoolContextChanged` (`failed-precondition`) and writes no unit, receipt or audit event of its own; an earlier committed attempt of the same request, if any, stands (attempt scope, section 6). This applies identically to a first create and to a same-key replay.
- **Never authority.** The field is only compared. The school written to the unit, the receipt id and record, and the audit event is always the server-verified one. `schoolId` itself remains a rejected server-owned request field, and every authorization refusal (section 4.1, including a transfer committed between the pre-check and the transaction, which is `claim-state-mismatch`) still applies first.
- **Idempotency unchanged.** Neither the field nor the A3-3 `compatibility` envelope is part of the request hash or the receipt identity: an accepted value always equals the receipt's own school. (Historical: under U2.2 a legacy request without the field and a school-bound request with the same key and payload replayed each other.) Concurrent same-key requests still admit exactly one unit.
- **After a refusal.** The original unit (if the first dispatch committed) stays in school A. If the teacher's school becomes A again, the same bound key replays it. A teacher who still needs the unit in B creates it there with a new key, as an explicit new intent.
- **Proof.** `teacher-units.emulator.test.ts`, "school binding: expectedSchoolId (U2.2 P1-B)", runs the real handler against the Firestore emulator: create and replay in A; lost response plus transfer to B refused with no unit, receipt, or audit in B; transfer committed between pre-check and transaction; transfer back to A replays; mismatched initial create writes nothing; since A3-3, a create without the field is refused on first attempts and replays (case 6); malformed values rejected with no write; authorization and membership refusals intact; concurrent bound requests admit one unit. With the comparison removed, the transfer, mismatch, and authorization cases fail.

## 6. Revision and concurrency contract

- A new unit has `revision: 1`.
- Every accepted state-changing mutation increments `revision` by exactly 1, in the same Firestore transaction that compares it.
- Each mutation runs in one transaction: authorization snapshot (section 4.1) -> read the unit -> verify ownership -> compute the change -> compare `expectedRevision` -> write the change, `revision + 1`, server `updatedAt`, and the audit event.
- **No-op rule.** Full authorization and ownership are verified first. Then, if the request's result already holds (same title/description, archive of an archived unit, restore of an active unit, the stored resource list, every unit already at its requested position), nothing is written, the revision and `archivedAt` are unchanged, no audit event is written, the current revision is returned with `noop: true`, and `expectedRevision` is not compared. A genuine no-op attempt writes nothing and creates no duplicate write or audit; nothing can be overwritten by a write that does not happen. When an SDK rerun reports a no-op because an earlier attempt of the same request already committed, that earlier write and its single audit event stand (attempt scope, section 6). This makes a retried archive or restore safe after a lost response.
- **Conflict.** Otherwise a mismatched `expectedRevision` is refused with `teacherUnits.writeConflict` (HTTPS `already-exists`) and `details.currentRevision`. The refusing attempt writes nothing (attempt scope, section 6). Transaction contention that exhausts Firestore's retries is also reported as `teacherUnits.writeConflict` (without `currentRevision`).
- Concurrency outcomes (U1A and U1B alike). Every operation is one Firestore transaction; the outcome of concurrent requests is whatever Firestore's transaction serialization produces, and this contract does not promise that a given pair always succeeds or always fails. What is guaranteed:
  - **Conflicting state-changing writes** to the same unit from the same revision cannot both commit. The loser's transaction is retried by Firestore, observes the new revision, and is refused with `teacherUnits.writeConflict` (or `teacherUnits.invalidStatus` when the winner archived the unit). Nothing is overwritten; the refusing attempt writes nothing (attempt scope, section 6).
  - **Identical requests** (same rename, same archive or restore, same resource list, same unit order) may produce one state-changing write and one authorized no-op: the second, retried against the new state, finds its result already holds (`noop: true`, no write, no audit event). This is the U1A no-op rule applied under concurrency.
  - **Operations on different state** (two different units, two grades, two teachers' organizations, a create in another grade) do not contend and succeed in a valid serialized order.
  - **Create, restore, and reorder in the same grade** follow serialization: if the create or restore commits before the reorder's snapshot, the reorder no longer names the complete organization and is refused with `teacherUnits.writeConflict` (that attempt writes nothing; attempt scope below); if it commits after, both succeed and the created unit sits at position 0 (a restored unit at its preserved position). Either outcome is valid.
- Client timestamps are never used for conflict detection.
- **Attempt scope.** Statements in this document that a refusal, replay or no-op "writes nothing" describe the transaction attempt that produced the response, not necessarily the whole request.
- Every refusal is raised inside a transaction attempt before that attempt stages any write, or before any transaction starts. A refused attempt performs no write of its own. Only a refusal decided before any transaction starts proves the request wrote nothing. Under the approved A3-3 Option A, the Firestore SDK may rerun a transaction after a commit error whose outcome is unknown, so an earlier attempt of the same request may already have committed. A later refusal does not roll that write back: the record, revision and audit event it committed stand. When the server cannot establish whether an earlier attempt committed, the outcome stays uncertain, and the client must treat an in-transaction refusal as unresolved (A3-4 S2, integrated on main; see "U2.6 A3-4 client migration"). Neither the server nor the client resubmits a request automatically after an uncertain outcome; only the SDK's own bounded reruns occur, and each rerun repeats every authorization and availability check.

## 7. Security boundaries

Firestore Rules (`platform/firebase/firestore.rules`):

**Callable-only (A3-5; implemented in the repository, not deployed).** No client may read or write any Teacher Units document directly. The `teacherUnits*` callables are the sole readers and writers (Admin SDK, which bypasses Rules), so every management read passes the A3-3 transactional availability and release-authority enforcement. A direct client read would skip that enforcement, so it is refused for every role, including the owning active teacher.

- `teacherUnits/{unitId}`: explicit `allow read, write: if false;`. Before A3-5 the owning active teacher at their current school could `get` and scoped-`list` their own units directly; that allowance is removed. The callables still enforce ownership, current school, district and availability.
- `teacherUnitCreateReceipts/{receiptId}`, `auditEvents/{eventId}`, `platformConfig/{configId}` (including `teacherUnitsAvailability`): existing explicit denies, unchanged.
- `teacherUnitsBackendReleases/{id}`, `teacherUnitsReleaseEvidence/{id}`, and any subcollection under a Teacher Units document: no block of their own; the terminal `/{document=**}` deny refuses them. No other block in the file matches them, so no allow can overlap. Collection-group queries over any of these collections are refused by the same terminal deny.
- Tests (`platform/firebase/tests/teacher-units.rules.test.ts`): get, list (including the formerly allowed `teacherId` + `schoolId` query), create, update and delete on every path above, plus collection-group queries, for unauthenticated callers, the owning active teacher, another teacher in the same school, a teacher in another school, a suspended owner holding a stale token, a student and a platform administrator. Against the pre-A3-5 Rules exactly the three owner get/list cases fail, confirming that every other path was already denied.

Audit: `teacherUnits.created`, `teacherUnits.updated`, `teacherUnits.archived`, `teacherUnits.restored`, and (U1B) `teacherUnits.resourcesUpdated` (payload adds `previousResourceCount`, `resourceCount`) and `teacherUnits.reordered` (one per moved unit; payload adds `previousSortOrder`, `sortOrder`), written in the same transaction as the change (target type `teacherUnit`), attributed to the in-transaction verified school and district. Payloads carry only `grade`, the revision(s), and for updates the changed field names. They never carry the title or description text. A replayed create and a no-op mutation emit none.

## 8. Archival semantics

Archive and restore are reversible status transitions of the same document. They preserve the unit id, owner, school, grade, title, description, `resourceIds`, `sortOrder`, and `createdAt`. Neither deletes the document or touches any assignment. Restore sets `archivedAt` back to `null`; the archive history is in the audit events. An archived unit cannot be edited (title, description, or resources) until it is restored, and a reorder never writes it.

## 9. Resource membership and ordering (U1B)

### 9.1 Membership: `teacherUnitsSetResources`

The request carries the complete ordered `resourceIds` the unit should hold; adding, removing, and reordering resources are all this one operation, one revision, and one audit event. It runs through the U1A compare-and-set core (`mutateOwnedTeacherUnit`), so authorization snapshot, ownership, no-op, revision, and audit behavior are exactly section 4.1 and section 6.

Validation runs before any read or write, and any failure refuses the whole request with nothing written:

- `resourceIds` must be an array of strings, at most `TEACHER_UNIT_RESOURCES_MAX` (100) (`teacherUnits.invalidResourceIds`);
- no id may repeat within the unit (`teacherUnits.duplicateResource`, `details.resourceId`);
- every id must be RA-1 `unitPlaceable` (`teacherUnits.resourceNotPlaceable`, `details.resourceIds` lists every failing id). Unknown ids, gated resources (for example the gated lesson `ragebaiting`), and reusable tools (`lab-report-assistant`) all fail.

Approved semantics:

- Placement requires `unitPlaceable` only. It does **not** require `authenticatedAssignment`: Gravity Wells (`simulation-gravity-wells`) is placeable and stays unassignable. Placing a resource does not make it assignable.
- A resource may appear in any number of units (the teacher's own units in any grade, and co-teachers' units). There is no cross-unit uniqueness check or index.
- Membership is not restricted by the resource's grade; the approved rule is placeability alone.
- An archived unit refuses with `teacherUnits.invalidStatus`. Archive and restore preserve `resourceIds` exactly.
- A list identical to the stored one (same ids, same order) is a no-op. Validation precedes the no-op check, so a list naming an id that is no longer placeable is refused even if it matches the stored list; the teacher removes the id by sending the list without it.
- Stored ids are not rewritten when the curriculum changes. A resource that later stops being placeable remains in existing units until a teacher saves the unit without it.

### 9.2 Ordering: `teacherUnitsReorder`

A teacher-grade organization is every **active** unit the caller owns, in their current canonical school, for one grade: exactly what `teacherUnitsList({ grade })` returns. Co-teachers and other grades are separate organizations.

The request names that complete set in the desired order, each unit with the `expectedRevision` the caller last observed (at most `TEACHER_UNITS_REORDER_MAX`, 200). Unit `i` (0-based) receives `sortOrder = i + 1`. In one transaction:

1. re-verify the caller's canonical authorization (section 4.1);
2. read the caller's units with the same `teacherId` + `schoolId` query as list (no new index) and keep the active units of the grade;
3. any requested id that is not one of them is refused with the uniform `teacherUnits.notFound` (missing, another teacher's, another school's, another grade's, or archived); a request that omits one of them is refused with `teacherUnits.writeConflict` (the caller's view is stale, for example a unit was created or restored since);
4. if every unit already holds its requested position, the attempt writes nothing (`noop: true`, revisions not compared; attempt scope, section 6);
5. otherwise every requested `expectedRevision` must match (`teacherUnits.writeConflict`, `details: { unitId, currentRevision }` for the first mismatch);
6. each unit whose position changes gets its new `sortOrder`, `revision + 1`, a server `updatedAt`, and one `teacherUnits.reordered` audit event, all in the same commit. Units whose position does not change are not written.

Malformed requests (empty list, repeated unit, entry not `{ unitId, expectedRevision }`) are refused before any read (`teacherUnits.invalidUnitOrder`, `.invalidUnitId`, `.invalidExpectedRevision`, or `.invalidRequest`).

Concurrency (section 6): two **different** reorders of one organization from the same revisions cannot both commit. Each reads every unit in the organization, so the loser's read set moved; Firestore retries it, and the retry is refused on revision. Two **identical** reorders may produce one write and one authorized no-op. A reorder compares the revision of every unit it names but writes only the units whose position changes, so a concurrent edit to a unit the reorder **moves** conflicts with it at that unit's revision (they cannot both commit from the same revision), while an edit to an **unmoved** unit may succeed alongside the reorder: if the reorder serializes first, both commit; if the edit serializes first, the reorder's comparison fails and that attempt is refused without writing (attempt scope, section 6). A concurrent create or restore in the grade follows section 6 (serialization-dependent). A reorder that commits rewrites each moved unit's revision, so a client holding an older revision for one of those units must reload before its next edit.

Ordering decisions (current behavior, recorded for review; not changed without approval):

- **New units start at position 0.** Create is unchanged from U1A, so a unit created after the last reorder sorts ahead of the ordered units (positions 1..n), in creation order, until the next reorder, which must include it.
- **Restored units retain their previous position.** Archived units are outside the organization and are never written by a reorder; a unit keeps its `sortOrder` through archive and restore and is placed by that preserved value until the next reorder includes it.
- **Ties are deterministic:** equal `sortOrder` values are ordered by `createdAt`, then `unitId` (for example two new units at 0, or a restored unit whose preserved position equals another unit's).
- **A complete reorder supports at most 200 active units** (`TEACHER_UNITS_REORDER_MAX`) per teacher-grade organization.

Post-commit response: the same contract as U1A mutations. The response is produced by an authorized read (`listOwnedTeacherUnits`) after the commit; a revocation between the commit and that read refuses the response while the reorder stands.

### 9.3 Authoritative placement validation and drift prevention

Functions cannot import the client curriculum bundle, so the server validates against a generated copy of one RA-1 field: `platform/functions/src/teacherUnits/unit-placeable-resources.json` holds the canonical ids for which `getFlatResources()` (`app/src/curriculum/resourceProjection.ts`) reports `unitPlaceable: true`, in canonical registry order (62 ids today). `unit-placeable-resources.ts` loads it into a frozen set and refuses to load an empty list or a duplicate id. It carries no resource data and is not a registry; RA-1 remains the single derivation of placement eligibility (`FLAT_RESOURCE_PROJECTION.md`).

**Required parity gate.** `scripts/unit-placement/check-parity.cjs` is the release invariant. It (1) runs `build-curriculum-manifest.cjs --check`, because RA-1 reads the generated manifest; (2) bundles and evaluates the real RA-1 accessor with the app's esbuild (it does not re-derive placement); (3) requires the server file to have exactly `description` and `resourceIds` and to equal the canonical ids, order included. An empty canonical list (zero placeable resources, which the server loader would refuse), noncanonical, non-placeable, stale, missing, duplicated, or reordered ids, a missing or malformed file, or missing app dependencies all fail closed (exit 1) and print the exact replacement list. It is invoked by every supported path:

| Path | How the gate runs |
| --- | --- |
| Any Functions build: `npm --prefix platform/functions run build`, CI, and the Functions `predeploy` of every `firebase deploy --only functions[...]` (including single-function deploys) | `prebuild` script in `platform/functions/package.json` |
| Any Hosting deploy: both targets, a single target, production (`firebase.json`) or staging (`firebase.staging.json`) | `build-pair.cjs` (the only Hosting `predeploy`) runs it before building, and records `unitPlacement: { count, fingerprint }` in `dist/hosting-release/pair-build.json` |
| `scripts/hosting-release/prepare.cjs` | through the pair build, plus the gate's test suite in its Hosting tests, plus app verify (`unitPlaceableManifest.test.ts`) |
| Platform CI (`.github/workflows/platform-ci.yml`) | explicit "Unit placement parity" step (gate and its tests) and the `prebuild`; the workflow also triggers on the RA-1 inputs (`app/src/curriculum/**`, the curriculum build scripts, `app/package*.json`, root `index.html`) and on `scripts/unit-placement/**`, as well as on `platform/**` (which includes the server file) |

Consequence: Functions release checkouts now need app dependencies installed (`npm --prefix app ci`), as Hosting release checkouts already do; without them the Functions build refuses. `scripts/unit-placement/check-parity.test.cjs` proves the gate refuses each drift class and that each entry point above invokes it.

**What the gate does not prove.** It checks the source tree being built. It does not prove which placement list a deployed Functions or Hosting artifact carries, and Hosting and Functions remain separately deployable. Today the effect of a deployed mismatch is bounded: the server list is the only enforcement, no teacher UI calls these callables yet, and a mismatch can only make the server refuse (`resourceNotPlaceable`) an id a future client offers, or accept one it does not offer; it cannot admit a resource outside the server's own deployed list. Deployed-version coordination is deferred as a mandatory U2 activation safeguard (section 11).

The app test `app/src/curriculum/unitPlaceableManifest.test.ts` remains as a fast developer check in `npm --prefix app run verify`.

## 9.4 U2.2 My Units client (gated, not active)

**Status:** implemented in the repository behind `TEACHER_UNITS_GATE_OPEN = false` (`app/src/index.ts`). Not active and not deployed. Opening the gate requires the U1A/U1B Functions and Rules to be deployed first, and separate authorization.

- **Surface.** Curriculum shows a Browse | My Units switch (`shell/surfaces/curriculum.ts`, panel in `shell/surfaces/teacherUnitsPanel.ts`) only when the entry point supplies the `teacherUnits` seam. With the gate closed the seam is `null`: no switch, no `teacherUnits*` call, no create-recovery storage access, and the Curriculum DOM is unchanged. My Units is not a top-level navigation item. Its history entry is `shell-curriculum-units` (`#curriculum/units`).
- **Scope.** Grade 6/7/8 listing, show-archived toggle, create, rename, edit description, archive, restore, and (U2.3, section 9.5) resource membership, and (U2.4, section 9.6) resource ordering within a unit. The controller is created lazily on first open, defaulting to the active Curriculum grade filter; "All" falls back to Grade 6 because the teacher-level saved default grade was removed in Sprint 28.6F.
- **Authority.** `teacherUnits/unitsController.ts` displays only server responses and sends the last server revision it holds. On `writeConflict` it fetches the unit with `teacherUnitsGet`, keeps the teacher's unsaved edits in the open editor, shows the current version, and waits for a deliberate save again. It never replays a stale revision.
- **Lifetime guard.** Every asynchronous continuation checks that the controller is still mounted and that the current Firebase uid still equals the mounted teacher, so a late response cannot update another account's UI.

### Durable create recovery

- **Store (attempt-keyed).** `teacherUnits/createAttemptStore.ts`: same-browser `localStorage`, one entry per create attempt, `lyfelabz.teacherUnits.createAttempt.v2/<uid>/<schoolId>/<idempotencyKey>` (uid and school percent-encoded; the key grammar has no `/`). An attempt is written, read back, and removed only under its own key, so one intent (in this tab or another) cannot overwrite or remove another's evidence. There is no cross-entry read-check-write sequence, so no atomicity across entries is relied on or claimed; Web Locks or IndexedDB transactions are not needed. Every write is read back byte-identical before it counts; every removal is verified. An entry holding anything other than the same attempt (same key, payload, context) is never replaced.
- **Strict validation.** A record is accepted only when it is version 2 and its grade, key grammar, title, and description pass the server's own rules (`teacherUnits/fieldRules.ts` mirrors `readTitle` / `readDescription`), its status and reason are consistent, and its stored key, teacher, and school equal the entry's scope. Anything else (including the pre-certification single-slot entry) is listed as unreadable: never replayed, never deleted automatically, and discarded only explicitly after an authoritative check.
- **Coordinator hooks.** The U2.1 `createUnitCreateCoordinator` gained optional `persistence`, `restore`, and `now` hooks. Without them it is the unchanged U2.1 state machine. With them, the attempt (key, exact payload, teacher/school context, status, `createdAtMs`) is saved and verified before first dispatch; if that fails, nothing is sent. Later transitions are saved best-effort: a failed save leaves the earlier in-flight record, which restores as unresolved, and the key stays in memory.
- **Resend refusals.** A pre-commit validation refusal of a same-key RESEND (reconcile) proves only that the resend did not commit. It never settles the attempt as rejected or removes its record: the attempt becomes unresolved `replayRefused`, reconcile is disabled, and it follows the check-then-set-aside path. Only a refusal of the first dispatch is a confirmed rejection.
- **Restore and discovery.** On mount the controller lists every attempt in its scope and gives each restored attempt its own coordinator. Before a new create it rescans, so an attempt saved by another tab blocks the form until resolved (a UX guard only; attempts that race past it each keep their own record). An in-flight record restores as unresolved ("uncertain", possibly committed). Reconciliation resends the same key and payload only when the live context equals the pinned one. A new key needs explicit new-unit intent.
- **Replay window.** Six days from `createdAtMs` (inside the approximately seven-day receipt retention, §5.3, with a day of margin; future-dated records are untrusted). Outside it the attempt becomes `replayExpired`: reconcile is disabled, the teacher must run an authoritative list check (all grades, archived included) before setting it aside, and an abandoned attempt keeps its "may already have been created" warning until explicitly dismissed. Nothing is deleted automatically.
- **Sign-out.** Records are not deleted on sign-out. They are only ever replayed under the same uid and school; another school's records of the same uid are only read for the informational former-school notices below.

### School binding (P1-B, resolved in the repository)

The cross-school duplicate described in section 5.4 is closed by the additive server field plus this client behavior (`teacherUnits/saveCoordination.ts`):

- **Capture.** The attempt's teacher/school context is pinned when the create intent begins (the coordinator reads the live session at `submit`, and the controller only returns it when it equals the mounted session). The durable record already stores it as `context.schoolId` (record version 2, unchanged), validated to equal the entry's scope.
- **Send.** Every dispatch, the first send and every reconcile (including a restored attempt after reload), carries `expectedSchoolId` equal to that pinned school. It is never re-read from the session and never replaced by a newly authorized school. A live context that differs from the pinned one still blocks reconciliation (`contextMismatch`) before anything is sent.
- **`schoolContextChanged`.** Classified as unresolved reason `schoolContextChanged` on a first dispatch or a resend: never a confirmed rejection, never deleted. The original key, payload, school, and durable record are preserved; reconciliation is disabled (`blocked: "schoolContextChanged"`), so nothing is resent automatically or against another school. Setting it aside requires the authoritative check, like `replayRefused`. The teacher sees: "We couldn't confirm whether this unit was created. Your school changed after you asked for it, so LyfeLabz won't create it at your new school. If it was created, it belongs to your previous school. Reload the page to continue at your current school, and create the unit there only if you still need it."
- **Old server (historical, U2.2).** A Functions deployment without the field rejects it as an unsupported field (`teacherUnits.invalidRequest`) during validation, before any transaction. On a first dispatch that is a confirmed pre-commit rejection (nothing written; the teacher cannot create until Functions are updated). On a resend it is `replayRefused`: unresolved, record kept, reconciliation disabled. The client never falls back to a request without the binding.
- **Compatibility (historical, U2.2 client).** `wire.ts` sends `expectedSchoolId` only when the caller supplies it, so existing U2.1 callers of `create` that omit it send the unchanged U2.1 payload. The U2.2 coordinator always supplies it.
- **Against the A3-3 server.** Since A3-4 S1 the client attaches the A3-3 `compatibility` envelope from each mutation's own permit, and since A3-4 S3 that permit comes from schema 2 discovery. A permit (and so an envelope) exists only when the backend declares an `enabled`, deployment-eligible policy that accepts `teacher-units-v2`; closed and unverified declarations refuse every mutation locally before dispatch. Production wiring still uses the UNCONFIGURED release-authority verifier, so no backend can currently declare `enabled` (see "U2.6 A3-4 client migration").

### Former-school notices (cross-school recovery visibility)

A teacher can start a create at school A, lose the response, and later be authorized only for school B. The school-A record stays in this browser under its own scope, and the school-B controller cannot reconcile it (section 5.4). Without discovery the teacher would never learn it exists. The correction is client-only (`createAttemptStore.listFormerSchools`, `unitsController` `formerSchool` state, `teacherUnitsPanel` "Unit request from a previous school" region):

- **Discovery.** On mount and on every rescan (before a new create, and on Check my units), the store enumerates existing `localStorage` keys under `lyfelabz.teacherUnits.createAttempt.v2/<uid>/` (and the legacy single-slot prefix) for the mounted teacher's uid, excluding the mounted school. Ownership comes only from the key's exact, percent-encoded uid segment, which must equal the Firebase uid the controller was mounted for; a record's own contents never widen what is listed, and a prefix-sharing uid never matches. Each entry is then strictly validated against the scope its key names (school segment must decode and re-encode canonically). No Firestore read, no callable, no school id from the browser is used for any authorization.
- **Read-only.** Discovery never writes, rewrites, re-scopes, or removes any entry; records stay byte-for-byte unchanged, including malformed ones. Storage failure reports `unavailable` (no notice, and the existing same-school storage guard still blocks create) and deletes nothing.
- **Informational only.** The region shows, for each valid attempt whose outcome is still uncertain (`inFlight`, `unresolved`, or set aside as `abandoned`), its title, grade, and start date, plus a count of unreadable former-school entries. It does not show the saved description or any school id. It has no controls: no Check again, reconcile, open, edit, restore, copy-into-a-new-create, or discard. It does not block the form: the teacher may deliberately create a new unit at the current school, which mints a new key and leaves the old record intact. Copy states that the outcome cannot be confirmed from the current school, that it will not be created again here, and to contact a school administrator if confirmation is needed; it never claims the unit was or was not created. Set-aside attempts are included and labelled "set aside": setting aside is not an acknowledgment of the outcome (the record, key, and uncertain reason stay stored, and the same-school UI keeps warning that the unit may exist). An attempt stops being listed only when its record is removed by the existing state machine: confirmation through reconciliation, or the explicit acknowledgment (Create another unit / dismiss) while authorized at its original school.
- **Lifecycle.** Notices are recomputed per controller, and a controller is bound to one uid and school, so a teacher or school change (a new controller) shows only that teacher's notices for that school. They persist across reloads until the attempt is resolved through normal recovery while authorized at its original school, after which they disappear on the next mount or rescan. The panel's polite status region (shared with other actions) is updated whenever the notice count changes: an increase is announced with the current count; a decrease replaces only the panel's own earlier notice message (with the new count, or "No unit requests from a previous school are listed now." at zero) and never overwrites an unrelated message; an unchanged rescan writes nothing; storage-unavailable clears the panel's own message without claiming zero. A teacher or school change mounts a new panel with an empty status; the region is labelled by its own heading and hidden (`hidden`) when empty.
- **Limits.** Discoverable only in the same browser, for the same authenticated teacher. Browser and device local only: an attempt made in another browser, profile, or device is not visible, and clearing site data removes the evidence. There is no cross-school replay or authorization capability, by design.

**Remaining activation prerequisites.** Unchanged by this correction: deploy and certify the Functions (with `expectedSchoolId`) and Rules first, then Hosting; independent certification of U2.2 including this correction; explicit authorization to set `TEACHER_UNITS_GATE_OPEN = true`.

**Rollout order (historical, U2.2): Functions before Hosting.** Superseded by A3-3, which makes the field mandatory and requires the `compatibility` envelope; the statements below describe the U2.2 server and do not hold for an A3-3 server. Deploy the `teacherUnitsCreate` Function that accepts `expectedSchoolId` first, then any Hosting bundle that sends it. A Hosting client that sends the field to an older Function cannot create units (every create is rejected as `invalidRequest`, safely, with no write). Functions can be deployed alone: the field is optional, so the current client is unaffected. Rolling back Functions while a field-sending client is live has the same safe-but-blocked effect. The gate (`TEACHER_UNITS_GATE_OPEN = false`) stays closed until both are deployed and certified.

## 9.5 U2.3 Resource membership UI (gated, not active)

**Status:** implemented in the repository behind the same closed gate (`TEACHER_UNITS_GATE_OPEN = false`). Not active and not deployed. No server, Rules, index, or Functions change: it is a client of `teacherUnitsSetResources` (section 9.1) through the existing U2.1 `setResources` wire adapter.

- **Catalog.** The picker lists `getPlaceableResources()` (`teacherUnits/placeableResources.ts`, the U2.1 adapter over RA-1 `getFlatResources()`), filtered to the unit's own grade (`filterPlaceableResources({ unitGrade })`) with an optional title search. Eligibility is RA-1 `unitPlaceable` only; nothing is inferred from type, public page, assessment, or `authenticatedAssignment`. Placeable resources that are not assignable (for example Gravity Wells) are offered and labelled "Can be organized here, not assigned". Grade 8 units show an empty state (RA-1 has no Grade 8 resources); grade eligibility is not broadened. The cross-grade discovery scope the adapter supports (`allGrades`) is not exposed. Labels are the Curriculum Browse labels (`FORMAL_RESOURCE_LABEL`, "Lesson").
- **Identity.** Requests carry canonical RA-1 ids only. The client refuses ids that are not placeable before sending; the server remains the enforcement boundary.
- **Add.** `unitsController.addResources(unitId, ids)` appends the ids not already in the held server list, in canonical registry order, and sends the complete list with the held `expectedRevision`. All-present is a no-op without a call; more than `TEACHER_UNIT_RESOURCES_MAX` (100) is refused before sending. The same resource may be in any number of units.
- **Remove.** `unitsController.removeResource(unitId, id)` sends the held list without that id. It affects only that unit; it never deletes a resource or touches assignments. An id the held unit no longer has is a no-op without a call.
- **Retired memberships (certification remediation).** A stored id that is no longer RA-1 `unitPlaceable` in this client is *retired*. The server refuses any list that still names a retired id (§9.1), so with retired ids present no add or single removal can succeed (two retired ids cannot be removed one at a time). The controller therefore refuses those requests before sending, and the card shows the retired rows ("A resource that is no longer available"), disables Add resources and the other Remove buttons, and offers **Remove N unavailable resources**. That control requires a second, explicit **Remove all N** / **Remove it** confirmation (Cancel sends nothing). `unitsController.removeRetiredResources(unitId)` then sends one `teacherUnitsSetResources` request: the held list with every retired id removed and the placeable ids in their existing relative order, with the held `expectedRevision`. Active resources, other units, the resource records, and assignments are untouched. Conflicts, uncertain outcomes, and archived units follow the rules below; after a conflict the new count is shown and confirmation is required again. Retirement is judged by the client bundle's RA-1 list; a deployed-list mismatch is the §11 activation prerequisite.
- **Order.** The list renders `unit.resourceIds` as returned (server order). Reordering is U2.4 (section 9.6).
- **Archived units.** Membership is shown read-only with "Restore this unit to add or remove resources." The controller refuses archived units before sending; a unit archived elsewhere is refused by the server (`invalidStatus`) and shown as archived. Archive and restore semantics are unchanged.
- **State consistency model (certification remediation, fourth cycle).** Responses may arrive in any order. One client clock orders events: every request reads it when dispatched, and a confirmed write also reads it when its response is received. (A) *Dispatch identity:* reads (list, get, Check my units, a create replay, and any no-op response, which wrote nothing) are stamped at dispatch, so a response never gains authority by arriving late. (B) *Confirmed-write precedence:* a write that committed (first create with `replayed: false`, update, archive, restore, membership change) is stamped on receipt, because its commit happened before the response arrived; only a read dispatched after that confirmation can outrank it, so a list that overlapped the write (possibly reading before the commit) never hides or rolls back a confirmed restore or create. (C) *Revision monotonicity:* the held record is replaced only by a higher `revision`, whatever the presence evidence, so a confirmed write's content is never discarded. (D) *Presence:* per unit the newest evidence is "present", "notActive" (omitted by an active-only list it was in scope for: archived, or gone, contents unknown), or "absent" (`notFound`, or omitted by a list that includes archived units). A list is evidence about its whole scope, including units the controller has not seen yet, so an older create replay or single-unit read cannot resurrect a unit a newer list omitted. An active-only omission says nothing new about a unit already held as archived. Older evidence never replaces newer evidence and any newer evidence does, so nothing is tombstoned. (E) *Projection:* the visible list is the "present" units of the selected grade and status; it is never evidence. `getUnitState(unitId)` reports the full state (active or archived with the full record, notActive, absent, unknown). List request sequencing (only the latest list request applies) is unchanged. This is client ordering only: authorization and `expectedRevision` remain server-enforced and nothing is resent. Known limitation: when another session changes a unit while this client's confirmed write and an overlapping read are both in flight, the write is shown until the next read dispatched after it.
- **Server contract and message fidelity (certification remediation, fifth cycle).** Every existing-unit write (update, archive, restore, membership) commits inside one transaction at exactly `expectedRevision + 1`; its response `unit` is a separate post-commit authorized read, so it can already include a later write by another session (`revision > expectedRevision + 1`), and a refusal of that read leaves the write standing. A no-op is built from the transaction snapshot: nothing is written and `expectedRevision` is not compared. A first create also returns a post-commit read; a replay reads the unit's current state in its transaction. An active-only list proves only "not active" for an omitted unit; a list with archived units (or Check my units) proves it absent. Consequences in the client: (1) a membership write's effect is taken from the request itself (`committed`: the sent list, its base list, and `expectedRevision + 1` on the `saved` result), never from the difference between the pre-request list and the post-commit record, so a resource removed elsewhere before that read never produces "Added 0 resources" and "changed somewhere else" is judged against the committed revision; (2) records and presence are ordered independently: absence evidence changes presence only, the highest-revision record is kept, and a later read that finds the unit again can never lower its revision or send a stale `expectedRevision`; (3) Check my units hints describe exactly the units that check returned (each with its latest accepted record), never a unit it omitted that a later or overlapping active-only load lists; (4) an outcome notice for a unit whose card is not shown (archived and hidden, refreshed away, or not found) is written to the panel's outcome region (`units-outcomes`, a dismissible `role="alert"` entry naming the unit; see the sixth-cycle entry for the per-operation policy) instead of a detached card, and a card that leaves the list hands its visible notice to that region; wording says where the unit's resources can be checked rather than "shown" when the card is hidden.
- **Authoritative absence and outcome preservation (certification remediation, sixth cycle).** Invariants: a retained record does not imply presence; visibility does not imply a unit can be changed; an active-only omission does not establish that a unit exists; a full-scope absence and an active-only omission are consistent, so in either arrival order the unit stays "absent" (the absence is never weakened into an actionable state); only a positive read restores presence; server ownership, school, revision, and status checks stay authoritative. Every mutation passes one gate (`mutate`): no held unit (never seen, or absent) is refused without a call; a held record that still says active while the newest evidence is an active-only omission is not acted on: the unit is read (`teacherUnitsGet`, never a resend) and reported as archived or changed, so the teacher decides again with fresh state; a held archived record (consistent with the omission) may be restored. Outcome region: every settled operation adds its own entry with a stable operation id; no entry is replaced by another operation's outcome (same unit or another); confirmations for units whose card is not shown are kept as polite `role="status"` entries (only the oldest confirmation is evicted beyond eight entries; problems are never evicted), problems are `role="alert"`; Dismiss removes only its entry. Notices are worded when shown or moved: a notice that moves out of a card leaving the list is reworded for where the unit now is (archived and hidden, no longer in your units, or not in the current list) and never says its resources are "shown".
- **Notice contract (architecture recovery, internally reviewed; not independently certified).** Retained card notices, durable entries and the shared membership status use a typed `NoticeText` with an immutable `historical` fact and optional `present(context)` wording. `wordNotice` combines them at presentation time. A confirmed write keeps its request-derived committed effect and count even when later records supersede it; a no-op keeps only "Nothing was changed." as history. Present membership, title, description, unavailable-resource validation, location and next steps are derived anew from the controller's accepted evidence. An inconsistent loaded record qualifies current knowledge without rewriting a confirmed commit as an uncertain operation. Historical operation titles stay historical; a renamed unit gets a separate latest-loaded-name sentence. Conflict values are identified as the latest version loaded and require the reconciliation revision or newer (the request base plus one after a failed read).
- **Evidence and display availability.** `getUnitState` is authority for presence; list readiness is only display availability. Every render reconciles notice descriptors, including while the list is loading or failed. Settled operations explicitly reconcile presentation because a record or absence can be accepted during an unavailable list without a list projection notification. Existing cards adopt accepted records while the display is unavailable; unconfirmed or absent cards expose no stale membership controls or current resource validation. A pinned editor survives but is distinguished from the filtered list. Absence has no retry, repair or restore instruction; archived guidance requires restoration; unknown state is qualified. An already visible card showing accepted contents remains a valid location during a refresh, avoiding transient notice churn.
- **Failure wording.** Authorization failure does not reveal whether it occurred before a transaction or during a post-commit read, so notices preserve uncertainty and never assert that the write was refused, committed or that the account currently lacks permission. Create recovery uses creation-specific uncertainty. List and Check my units errors describe failed reads, never uncertainty about a saved change. Duplicate-resource refusal names repeated submitted IDs, not prior unit membership. Placement refusals and picker-closure notices retain their historical cause while repair/restore instructions follow accepted state. Edit-preservation wording is evaluated from whether the editor remains open.
- **Identity, dismissal and announcements.** Stable operation ids, durable-entry ordering, independent Dismiss, alert/status roles, owner-only pending clearing, confirmation eviction and its focus correction retain their existing policy. Only changed notice text or dismissal labels are written. Shared status, list-error alerts and create-error alerts also avoid identical text writes. Details, the complete notice-path inventory, adversarial matrix and local evidence are in [U2.3 Notice Recovery](U2_3_NOTICE_RECOVERY.md). This is implementation and internal review evidence, not independent certification or activation approval.
- **Production context guard (certification remediation).** The surface seam previously compared only the Firebase uid. It now also requires the app's canonical active-teacher session (`readActiveTeacher`, bound in `index.ts` with `bootstrapActiveTeacherReader` to the run's own resolved session) to have the mounted uid **and** school. The reader returns that run's session only while the run is current and the app's `lastActiveTeacher` slot holds that same session object, so the previous run's cached teacher (for example the same uid at a former school while a school-transfer re-bootstrap is still hydrating) never counts as current. Any new bootstrap run (sign-out, account switch, re-bootstrap after a school transfer) returns null, so every pending add, remove, repair, refresh, or re-read response is ignored and no further request is sent from the old controller. The server still re-verifies teacher and school on every call; the client guard never grants anything.
- **Authority and concurrency.** Nothing is shown as added or removed until the server responds; the list always renders the last server unit. Requests go through the U2.2 `mutate` path: one mutation per unit at a time (`createMutationGate`; extra clicks are `busy` and the controls are unavailable while pending; since U2.5 they stay focusable with `aria-disabled`, section 9.7), `writeConflict` re-reads the unit with `teacherUnitsGet`, adopts it, and waits for a deliberate retry (the picker keeps the selection, minus anything now in the unit). A network failure or malformed response is reported as **uncertain**: the unit is re-read once and shown, nothing is resent, and the teacher is told the outcome could not be confirmed. A later attempt carries the re-read revision, so it cannot overwrite another session's change. A placement refusal (`resourceNotPlaceable`, `duplicateResource`) re-reads the unit and shows the refusal. Authorization refusals are shown and not retried. A teacher or school change while a request is pending makes the response stale (ignored), and later requests are not sent (existing lifetime guard).
- **No durable attempt evidence.** Membership is not stored in browser storage. Unlike create, a membership write is revision-guarded, so a lost response is resolved by reading the unit, not by a replay record. Since A3-4 S2 the client never resends it (section "U2.6 A3-4 client migration"); an uncertain request is kept as a memory-only pending record instead. The U2.2 create-attempt mechanism is unchanged and not extended.
- **Accessibility.** Add resources is a button with `aria-expanded`; the picker is a labelled form (heading, search field, fieldset with legend, native checkboxes) that opens with focus in the search field and closes on Cancel or Escape with focus returned to Add resources. Each Remove button names the resource and unit. Pending, success, and no-op outcomes use the panel's polite status region. Each request owns its pending message and, when it settles without a confirmation (conflict, uncertain, refusal, stale), clears only that message and only while it is still showing, so it never erases another card's pending or confirmation message. Membership messages follow from two facts only: what the response proves (`noop` means the server wrote nothing and is never called "saved"; otherwise the write committed) and what `getUnitState` holds for the whole unit now (never whether a card is shown: an archived unit may be hidden and still hold the resource). Presence or absence is claimed only when that state supports it; A changed-since explanation requires a revision newer than the committed revision for a write or the response snapshot for a no-op; live membership wording does not infer an external author from that revision. Unknown current contents are qualified; known historical outcomes are preserved. Authoritative absence receives no refresh/retry instruction. A stale response announces nothing. An open picker follows the current unit: when the unit is archived or now holds unavailable resources it closes (focus moves to the repair or the first card control), the card explains why, the detached form cannot submit, and every submit re-checks eligibility against the current unit. Check my units hints ("Found N ... named ...") are matched against the latest accepted units, not the check response as it arrived, so a rename or refresh since is reflected; the attempt's own stored title and former-school notices are unchanged. Failures use the card's alert notice. After removal, focus moves to the next Remove button or to Add resources.
- **Activation prerequisite (unchanged).** Section 11 "Deployed-version coordination" applies to this surface: before the gate opens, a mechanism must prove the deployed Functions placement list matches the client's offered choices. U2.3 does not implement it.
- **Out of scope.** Assignment publication, Classroom, `unitContext`, completion, scoring, passback, Current assignment selection, student grouping, study materials, and ordering (U2.4, section 9.6).

## 9.6 U2.4 Resource ordering UI (gated, not active)

**Status:** implemented in the repository behind the same closed gate (`TEACHER_UNITS_GATE_OPEN = false`). Not active and not deployed. No server, Rules, index, Functions, RA-1, or publisher change.

- **Contract.** Resource order inside a unit is the `resourceIds` sequence (section 9.1). `sortOrder` orders units within a teacher-grade organization (section 9.2) and is never written by U2.4; `teacherUnitsReorder` is not called. A move is one `teacherUnitsSetResources` request carrying a permutation of the held list.
- **Interaction.** Each resource row of an active unit with two or more resources has native **Move up** and **Move down** buttons. There is no drag-and-drop, no move to top or bottom, and no separate Save Order step. Units with zero or one resource show no move controls; archived units are read-only.
- **Immediate save, server authority.** `unitsController.moveResource(unitId, resourceId, "up" | "down")` computes the next list with `unitOrderMath.moveIdByStep` from the record held at dispatch and sends it with that record's revision, through the same `setMembership` / `mutate` path as add and remove. The row moves only when the server's response is accepted. Unknown ids, boundary moves, and lists shorter than two are no-ops without a call.
- **Concurrency.** One mutation per unit at a time (`createMutationGate`): while a move, add, or remove is pending, every move control of that unit is blocked and further clicks send nothing. A resource added or removed, or a reorder made, in another session raises the revision, so a move computed from the older list is refused (`writeConflict`); the controller reads the unit, adopts it, and waits for a deliberate new move ("This unit changed since it was loaded here, so nothing was moved." since U2.5; section 9.7). A stale move therefore cannot drop a resource added elsewhere. A lost response is reconciled by one read and is never resent. Late reads never roll back a confirmed move (section 9.5 state consistency model). Account and school guards are unchanged.
- **Retired resources.** The server refuses any list that names a retired id, even a pure permutation. While a unit holds retired ids, no move controls are shown, the controller refuses `moveResource` before sending, and the existing repair note says to remove the unavailable resources "before adding, removing, or reordering other resources". The confirmed **Remove N unavailable resources** repair is unchanged; nothing is removed silently.
- **Notices.** Moves extend the section 9.5 notice contract (`membershipOutcome` action `move`). The historical fact is `Moved "<resource>" to position <p> of <n>.`, computed from the committed list (`committed.resourceIds`), never from the post-commit response. The present wording (where the resource is now, whether the unit changed, archived or absent, list loading or failed) is derived anew from accepted controller state on every render. A no-op is "Nothing was changed.". Conflicts, uncertain writes, authorization refusals, archived refusals, and retired-resource refusals reuse the existing membership notices with "nothing was moved".
- **Accessibility.** Native `<button type="button">` controls with names such as "Move Plate Tectonics up in Earth Systems". Boundary controls and controls blocked by a pending request use `aria-disabled="true"` (not `disabled`), so keyboard focus stays on them; their activation is ignored. After a settled move, focus returns to the same resource's control in the same direction, or the opposite direction when the resource has reached a boundary, never the document body. The ordered list (`<ol>`) is kept. Outcomes use the panel's polite status region. On coarse pointers the existing 44px minimum applies; at 480px and below the controls wrap beneath the resource title.
- **Activation prerequisites (unchanged).** The gate stays closed. Opening it still requires the U1A/U1B Functions and Rules deployment, the section 11 deployed-version placement coordination, and separate authorization.

### Focus ownership

- **Only real targets.** Focus is moved only to a connected, enabled element with no hidden ancestor. A detached or disabled candidate is skipped; every focus request names an ordered list of candidates.
- **Pending operations keep focus.** While a unit has a request in flight, its controls (Add resources, Edit, Archive, Restore, Remove, Move up/down, Remove unavailable resources and its confirmation, editor Save and Restore, picker Add selected and checkboxes) stay focusable with `aria-disabled="true"`; they are not natively disabled, so the pressed control keeps focus. One capturing click guard on the panel ignores activation (click, Enter, Space) of any `aria-disabled` control, and the editor and picker submit handlers check the same state, so Enter in a field cannot submit either. The controller's per-unit mutation gate still refuses a second request (`busy`). While a create is pending, its fields are read-only and its submit is `aria-disabled`. Structural blocks (nothing selected, unavailable resources present, an archived unit's Save, unconfirmed create requests) remain native `disabled`.
- **Settled operations do not steal focus.** When a request settles, it moves focus only if focus is still the operation's own: inside its card, on the destination the panel chose when its card left the list (until the teacher moves), or lost (the document body). A teacher who navigated elsewhere keeps their focus. Overlapping operations each check their own card; a stale or disposed response does nothing.
- **Destinations.** Archive and restore while the card stays listed: the replacing control (Restore after Archive, Archive after Restore). Remove: the same row, else the row that took its place, else Add resources. Move: the same resource's control (U2.4 rule). Add: Add resources after the picker closes. Edit Save: the card's Edit. Validation: the invalid field. Create: Create another unit; an unconfirmed create: Check again or Check my units. Both apply only while focus is still in the create area or lost; the outcome is announced either way.
- **Card departure.** Before a card that holds focus is removed (archived while archived units are hidden, archived elsewhere and found by a read, deleted or no longer in this school's units, filtered out), focus goes to the main action of the card now at its position (else the card before it), else the newest outcome-region Dismiss for that unit, else the **My Units** heading. A pinned editor leaving with Cancel follows the same rule. Any other control a render disables, hides, moves, or removes while it holds focus is returned to itself when still usable, else its card's main action, else the heading.
- **Stable rendering.** A card body is rebuilt only when what it shows changes: the accepted unit record (records are replaced, never mutated, so identity is the change), presence, an editor or picker opening or closing, the unavailable-resource confirmation, or (for a unit no longer listed) where it is. Busy state is applied in place. Picker options are rebuilt only when the unit record or search changes. Unaffected cards keep their DOM nodes; titles, labels, order, membership, archive state and context notices still update because each comes from a new record or from the unchanged notice refresh. There is no second state authority: the signature only records which controller record the DOM was built from.

## 11. Known limitations

- Units created at a teacher's previous school are retained but unreachable by that teacher after a transfer; U1A has no recovery or transfer operation.

- `teacherUnitsList` returns everything in one response up to 1000 units per teacher per school (archived units count toward the ceiling); there is no pagination.
- Post-commit revocation (section 4.1) can leave a committed write whose response was refused; for creates, the key replays it once the caller is authorized again.
- A grade organization larger than 200 active units cannot be reordered in one request.
- The server placement list is a deploy-time copy (section 9.3): after a registry change, membership validation follows the new list only once Functions are redeployed.
- **Deployed-version coordination: deferred, mandatory U2 activation safeguard.** The parity gate proves source-tree parity only; it does not prove which placement list deployed Functions or a deployed (or cached) Hosting client carries, and Hosting and Functions remain independently deployable. Nothing is implemented in U1B. Before U2 activates any client surface that offers placement choices, a coordination mechanism must be designed, approved, and certified that accounts for:
  - a shared clean source commit for the Functions and Hosting releases;
  - the eligibility fingerprint (SHA-256 of the ordered RA-1 placeable ids, printed by the gate and recorded in `pair-build.json` as `unitPlacement.fingerprint`);
  - the actual deployed Functions fingerprint (observable from the running server, not assumed from source);
  - the deployed Hosting artifact fingerprint;

## U2.6 A2 authenticated compatibility safeguard

> **Historical (superseded by A3-3 on the server).** This section records the A2 contract as certified. The A3-3 server no longer accepts the schema 1 / `teacher-units-v1` capability request (it is refused with `teacherUnits.contractUnsupported`) and never returns a schema 1 response; A3-3 also replaces the A2 emulator identity rules. The client discovery described here was replaced by A3-4 S3 schema 2 discovery (see "A3-4 S3 schema 2 discovery"); the client no longer sends a v1 request, and local origins no longer map to an emulator. See "U2.6 A3-3 transactional backend enforcement" below for the current server contract.

A2 adds `teacherUnitsCapabilities`, an authenticated, read-only callable. It
requires the existing canonical active-teacher authorization and rechecks the
school/district context in a read-only transaction. It writes no unit, receipt,
audit or other persistent record. It does not change the eight existing request
contracts or their authorization. Production Teacher Units remains closed by
`releaseAvailability.ts` and the controlled application compiler; A2 provides no
activation switch or enabling server availability flag.

### Capability contract

The closed request is `{schemaVersion:1, nonce, clientContractVersion:"teacher-units-v1"}`.
The nonce must be 16–64 URL-safe alphanumeric/underscore/hyphen characters. Unknown
keys, unsupported versions and malformed requests use existing platform errors.

The response has exactly these fields:

- `schemaVersion:1`, and the echoed `nonce`.
- `backend:{projectId,environment,region}`.
- `teacherUnits:{apiContractVersion,supportedOperations,acceptedClientContractVersions,placementFingerprint}`.
- `caller:{uid,role:"teacher",schoolId,districtId}`.

The initial API/client contract is `teacher-units-v1`. Supported identifiers are
`create`, `list`, `get`, `update`, `archive`, `restore`, `setResources`, `reorder`.
They describe implementation, not availability or an authorization grant.
The placement fingerprint is lowercase SHA-256 of UTF-8 `JSON.stringify` of the
ordered canonical placeable IDs, matching A1's placement algorithm. The browser
computes its expectation from the real RA-1 projection. Contract versions describe
wire semantics; they are not source revisions or artifact attestations.

Runtime identity cross-checks every supplied project ID from `GCLOUD_PROJECT`,
`GOOGLE_CLOUD_PROJECT`, JSON `FIREBASE_CONFIG`, the Admin app and resolved Firestore
project. The resolved Firestore getter is checked at runtime because Firestore 7
omits it from public typings; unknown SDK shapes refuse. Missing, malformed or conflicting identity refuses. The explicit mapping
is production `lyfelabz-prod`, staging `lyfelabz-staging`; emulator mode additionally
permits `demo-bootstrap` for synthetic transport tests. Emulator classification
requires `FUNCTIONS_EMULATOR=true`. The callable explicitly deploys to
`us-central1`; a contradictory supplied `FUNCTION_REGION` refuses.

### Client identity, dispatch and lifetime

The trusted expectation comes from exact independent origin pins:
`https://app.lyfelabz.com` → production; `https://lyfelabz-staging.web.app` → staging.
HTTP localhost/127.0.0.1 permits the existing local `lyfelabz-prod` emulator
configuration, Auth at 127.0.0.1:9099 and Functions at 127.0.0.1:5001. Unknown
preview origins, HTTPS local origins and 0.0.0.0 refuse Teacher Units verification.
Injected Firebase configuration is checked against these expectations; it cannot
supply the trusted expectation. The transport harness's demo project is not an
approved browser project.

Teacher bootstrap obtains Functions explicitly from `auth.app` in `us-central1`.
The verifier checks actual Auth/Functions app object identity, project ID, region,
absence of a custom Functions domain and exact emulator configuration. It also
checks Firebase 10's internal `FunctionsService.emulatorOrigin` field; a missing
or changed SDK shape refuses rather than assuming production transport. An SDK
upgrade must review this check. An unexpected reused default app is refused for
Teacher Units; A2 does not redesign global bootstrap behavior.

All six mutations and explicit retries capture their existing payload before
awaiting verification. Each obtains a fresh authenticated response, validates
nonce/schema/versions/all eight operations/project/environment/region/canonical
caller/placement, then rechecks bootstrap generation, current user, school, app
and transport immediately before dispatch. District expectation comes from the
current signed token: the endpoint independently verifies it against canonical
records. Token values are compared before and after the handshake, and a temporary
ID-token observer invalidates account/token transitions, including same-UID
reauthentication. The observer stays active through final permit consumption.

Verification has a ten-second deadline covering token reads, hashing and the
capability request. A delayed result cannot cause later mutation dispatch. There
is no positive cache, shared verification or automatic replay. Each mutation adds
one capability network call; token SDK reads may refresh a token. `list` and `get`
retain existing authenticated read behavior, allowing recovery checks without a
capability dependency. All eight operation identifiers are still required for a
mutation to pass compatibility verification.

A local `TeacherUnitsCompatibilityError` denotes failure before dispatch. A first
create blocked there is a confirmed rejection, not an uncertain save. A blocked
resend preserves the earlier key, school, uncertainty reason and reconciliation
restrictions. A server-supplied matching code cannot impersonate this local error.
Once dispatched, existing response validation, idempotency, revisions, no-ops and
uncertain-outcome handling remain authoritative. Durable create-attempt storage
continues to precede dispatch: a browser crash during verification can restore an
in-flight record as uncertain, conservatively, until recovery checks resolve it.

### Evidence limits and A3 boundary

A compatible capability response describes its own endpoint; it does not prove
that the other eight independently deployed functions share its revision. A
mixed deployment may pass the handshake, and a deployment can change after the
check. Older cached clients can bypass A2 entirely. Modified JavaScript, malicious
extensions, XSS or interception can forge or bypass a client check. Nonces provide
correlation, not cryptographic backend attestation. A wrongly configured backend
can self-report a false contract; project strings are not independent attestation.

A1's release receipts, placement parity and exact backend-artifact observations
remain unchanged. They are timestamped release evidence, not live authenticated
compatibility. A2 does not replace A1 Management API checks or claim a deployed git
SHA/whole-package runtime fingerprint. The new endpoint is not added to A1's
certified eight-endpoint inventory in this change; extending that evidence scope
requires separate review. A3 owns server availability, authorization posture and
any mutation-side contract enforcement that closes bypass/version races. A2 does
not secure callable endpoints, change Rules, enable Teacher Units or certify a
live environment.

### A3-4 S2 uncertain-outcome reconciliation

Approved decisions: D1 memory-level persistence, D2 present-state wording, D3 no automatic or blind resend.

- **Certainty.** `isUncertainMutationFailure` (`mutationReconciliation.ts`) treats every failure of a dispatched revision-guarded mutation as uncertain except proven non-commits: never sent (`compatibilityBlocked`) or refused in request validation before any transaction (`invalidField`, `invalidRequest`, `resourceRejected`, `limitExceeded`). Network and unexpected failures are uncertain; the old `isSafeToResend` / `canResend` signal is removed, and their recovery is `refresh`, never `retry`.
- **Pending records.** `update`, `archive`, `restore` and `setResources` open an immutable record at dispatch (operation, unit, `expectedRevision`, the exact dispatched intent, title at request, timestamp, teacher and school scope). A confirmed success or a proven non-commit closes it; any other outcome keeps it as uncertain. Each request is transmitted exactly once.
- **One automatic read.** After `network`, `unexpected`, `unconfirmed`, `writeConflict` or `invalidStatus`, at most one automatic `teacherUnitsGet` runs (the existing membership reread is preserved, not doubled). Account refusals and `notFound` get no automatic read. A failed read leaves the finding unknown. A read never triggers a mutation.
- **Present-state evaluator.** `evaluateUnitReconciliation` compares the newest accepted record of the unit with the request: `consistentWithRequest` (the unit holds what was asked, at the base or a newer revision), `notInEffectNow` (same revision, does not hold it), `changedSince` (newer revision, does not hold it), or `unknown` (read failed, not found, not checked, or an older revision). Every evaluation carries `commit: "undetermined"`: none says whether the request committed, and revisions or timestamps never attribute a change to anyone.
- **Evidence ordering (certification remediation P2-2 to P2-4).** The scoped registry is also the shared evidence store of every controller of that teacher and school, and its logical clock is their clock: a read is stamped at dispatch, a confirmed write at receipt. Unit content is revision-monotonic per scope (a lower revision never replaces a higher one, whatever its stamp or completion order; an equal revision with the same content only raises the stamp at which it was last observed). An equal revision with different content is a conflict: freshness does not advance, findings for the unit become `unknown` (`inconsistent`), and the D3 guard stays, until a higher revision is observed. A record speaks to a pending entry when its revision is newer than the request's base or it was observed by a read dispatched after the outcome became uncertain. Every accepted record (list, get, Check my units, confirmed or no-op mutation responses, create results) re-evaluates the affected findings, so a later confirmed change or newer read replaces an older finding and a stale read never contradicts one. Each controller publishes what it accepts and adopts what the scope holds, with the original stamps, so a replaced controller's late reread or confirmed write reaches the current controller and an older remount list cannot overwrite it. A replaced controller never touches a newer panel directly.
- **Authoritative absence (second recertification F3).** A `notFound` read, or a successful list that is complete for the unit, establishes absence: a list is complete only when it included archived units and covered every grade or the unit's own grade (the server stamps a unit's grade at creation and never changes it, and refuses a list above its ceiling rather than truncating it). An active-only, other-grade, or failed list says nothing about absence. Absence is shared with every controller of the scope, stamped at dispatch and at receipt: a record outranks it only when read after the absence was received, or when its revision was first seen after the absent read was dispatched. The registry's rule (`isPresent`) is the only one: the controller's card, its record, the pending finding and the guard all follow it, in either completion order and across controllers and remounts (third remediation F2). Overlapping reads that this rule cannot order (an absence and a read of an already-known revision) are treated conservatively as absent, with an `unknown` finding, until a later read. A late `notFound` after a remount therefore removes the replacement's card, an overlapping read of the same revision never hides it, and a stale absence never hides a newer revision. Findings for an absent unit are `unknown` (`notFound`). Absence ordering uses client stamps; it is never read as evidence of who changed what.
- **Guard and finding use one rule (third remediation F1).** The finding and the D3 guard are derived from the same verdict. A read since the outcome that returns a revision below the request's base is inconsistent evidence (the base was read before the request was sent), so the finding is `unknown` (`inconsistent`) and the guard stays, however fresh the read; timestamps never override revision validity. The guard keeps the request's base revision itself, and the controller shares its held record as a revision floor when it sends a request, so pruning shared evidence can never open a lower-revision path. A consistent read at the base after the outcome supports deliberate recovery (`notInEffectNow`) without proving whether the request finished.
- **Guard lifecycle (fourth remediation).** A unit's uncertainty record (base revision floor and evidence metadata) is retained after it stops blocking, and whether it blocks is re-derived from the same verdict every time the unit's evidence changes. Later conflicting, below-base or otherwise inconsistent evidence therefore blocks again, whether or not the notice was dismissed, and counts toward capacity at once. The record is discarded only when the scope ends, or when a later STATE-CHANGING write to the unit, sent from eligible state, is confirmed by the server (fifth remediation). The backend contract (`teacher-unit-mutation.ts`, shared by update, archive, restore and setResources) decides this: a no-op writes nothing, leaves the revision unchanged and does not even compare `expectedRevision`, so it settles nothing; a state-changing write commits only when `expectedRevision` equals the stored revision and writes `expectedRevision + 1`. A confirmed write settles the earlier uncertainty only when it was begun after that uncertainty, its base is at or above the earlier request's base, and its OWN response shows exactly the transition the contract guarantees (revision = its base + 1), so the earlier request can never commit afterwards (sixth remediation). The proof is self-contained: an inconsistent response (a "write" whose revision did not advance, or advanced by more than one) is never repaired with revision evidence from a separate read, which may still support findings and eligibility. Because the post-commit response is a second read, a legitimate write that reports more than base + 1 (another write landed in between) does not settle either; the earlier record, its floor and its capacity slot stay, which is conservative. Only that structured, response-specific proof can retire earlier uncertainty or free retained capacity; no internal caller may settle with a bare flag (seventh remediation).
- **Inconsistent write responses (seventh remediation).** A non-no-op success whose unit revision is not above the request's base cannot be that request's commit (the contract commits base + 1 and then reads again). The controller treats it exactly like any other uncertain result: the pending record stays, nothing is resent, it is never announced as saved, the open editor keeps the teacher's input, its unit is not accepted as evidence, and further changes to the unit are blocked until current state is checked. It makes no automatic read itself (a replacement controller may still make the single one). A success above base + 1 is a valid save. A success response alone is never read as proof of whether the earlier request committed. An absence releases a guard only when its read was dispatched after the outcome became uncertain: an earlier read's `notFound` or complete-list omission, however late it arrives, is present-state evidence (the card shows the unit gone and the finding says not found) but never recovery. The refusal's own `notFound` is treated the same way.
- **D3 guard (P2-1).** After an uncertain outcome for a unit, `update`, `archive`, `restore` and `setResources` for that unit are refused in the controller (`needsCheck`, nothing sent) until an accepted, non-conflicting record newer than the request's base, or observed by a read dispatched after the outcome, exists. A failed read never lifts it, and neither does dismissing the notice. The guard is checked before every answer computed from held state, not only before a send (second recertification F1): a local no-op (an edit back to the held title, adding a resource the held list already has), an archived refusal, or an unavailable-resource refusal also returns `needsCheck`, never `saved` or a no-op. While any request for the unit is in flight, those answers are `busy`. Only the controller that sent a request makes its automatic read while it is current; another controller takes it over only once that one is gone. Check current state, Check for changes, or any later accepted read lifts it; the teacher then decides again. The card says the new change was not sent and keeps the editor's input.
- **Lifecycle (D1).** Records live in a registry owned by the Teacher Units surface seam, which the app builds once per authenticated bootstrap run, above the disposable panel and controller. They survive Curriculum navigation and panel remounts; a remounted controller shows them, treats a unit with an in-flight request as busy, and takes over the single automatic read if the original controller was replaced first. Records are scoped to teacher and school: binding another scope clears the previous one, and every write rechecks the live canonical context, so a late callback never writes into another account or school. Nothing is written to browser storage, so non-create teacher text is never persisted and a full reload starts with no records (it never reports an outcome as resolved).
- **Late results.** A response that arrives after the controller that sent it was replaced, but while the teacher and school are unchanged, still settles the record: an uncertain result stays pending, while a confirmed save, a no-op, or a definite refusal is kept as a one-time resolution (bounded) that the current panel announces, and its unit state is adopted by the current controller.
- **Teacher-facing recovery (D2, D3).** My Units shows an Unconfirmed changes region: what was asked, "This change wasn't confirmed.", and the present-state finding. Its intro says the list is kept only while the teacher stays on the page and that reloading clears it without confirming or undoing anything. Controls are Check current state (one deliberate `teacherUnitsGet`) and Dismiss. There is no resend control; a further change is a new teacher action from the unit, carrying the freshly read revision. Open editors keep the teacher's input. Card notices keep their S1 wording, except that Check for changes is described as showing the current state, never whether a change was saved.
- **Live status (P2-5, second recertification F4, F5).** The region holds a persistent polite status line (`role="status"`, `aria-live="polite"`) that is not rebuilt with the list. It announces, one message per change: on mount or remount, how many changes are listed; a restored request's outcome; any later change of a finding's teacher-facing wording (including a deliberate check); and late resolutions. The panel's own first uncertain outcome is left to its card alert. A message is tracked by its wording, so a newer revision that reads the same, or an ordinary re-render, writes nothing to the DOM. When an entry the message describes is dismissed or settled, its present-state wording is withdrawn (dismissal confirms, cancels and undoes nothing), and the region hides when it has neither entries nor a message. Verified as DOM semantics and DOM mutations in jsdom tests only, not with a screen reader.
- **Capacity (second recertification F6).** Per teacher and school: at most 100 entries (in flight or uncertain), 200 units whose guard currently blocks, and 900 retained uncertainty records (blocking or not); none is ever evicted. A guard that starts blocking again counts at once and may take the blocking count past 200, which only refuses new changes. The refusal names its bound, and the card offers only an action that can free it: dismissing reviewed notices for the entry bound (or waiting, when every entry is still in flight), Check for changes for the blocking bound, and for the retained-record bound a plain statement that reads and dismissals won't help and that reloading starts a new visit and clears this tracking, but neither confirms, undoes nor cancels changes already sent (they may still finish), and loses unsaved input. No change is ever suggested just to free room. At either limit a new change is refused before it is sent (`capacity`): the card says LyfeLabz didn't send it and keeps the editor's input, and the teacher checks current state (which lifts guards) or dismisses reviewed notices (which frees entries). Unit evidence is bounded at 1,000 units (the server's own list ceiling); evidence no entry or guard refers to is dropped oldest first, and a controller simply re-reads it. At most 20 late resolutions are kept. Guards are released the moment qualifying evidence for their unit is accepted (third remediation F3), so one successful refresh frees every eligible guard and capacity follows the guards actually retained; failed, conflicting, below-base or omitted-from-incomplete-list reads release nothing. The work is per accepted record, bounded by the entry limit. Controllers keep no per-request bookkeeping beyond in-flight units (F4).
- **Create and reorder.** Create keeps its durable idempotency record and same-key reconcile; each dispatch takes a fresh compatibility permit, and a compatibility refusal during reconcile sends nothing and keeps the attempt unresolved with its original reason. Reorder has no client consumer; `evaluateReorderReconciliation` provides its classification only.
- **Limits.** Records and shared evidence end with the bootstrap run (reload, sign-out, account or school change). An in-flight entry whose response never arrives keeps its unit busy until the Firebase callable times out. A `notFound` or account refusal is kept as uncertain because the server decides it inside a transaction. Absence is established only by a `notFound` read or a complete list; a unit that disappears from an active-only list is not known to be gone until such a read. After a reload the D3 guard is gone with the records, so a new change carries the revision the reloaded page reads.
